# SKD implementation corrections before post-attack evaluation

The first design was committed as
`5f152135e25cd0ce0a9079c5da2b555274b0d3d0`. Its real source-generation phase
completed 240 prompts × two schemes. The first two candidate pools were empty
because all proposal batches were rejected; a third pool had 15 selectable edits.
The inconsistent formatting exposed a software implementation gap in the promised
structured proposal interface.

A detector-free reproduction of the first rejected call showed a Markdown JSON
fence, 36 replacement fields emitted despite the requested limit of 12, and a
`length` finish reason at exactly 1,536 completion tokens. No silent JSON repair
or partial candidate salvage was performed.

The initial attempt at `results/004-skd/qwen-v030` was stopped, preserved, and
marked **invalidated**. Its `evaluation.jsonl` is empty. None of its candidate
pools or attack outputs enters the final result denominators. No post-attack
watermark scores existed or informed this correction.

## Corrected proposal interface

Protocol `skd-v2` enumerates canonical structurally safe 1–4 word source spans,
deterministically shuffles them using the public sample seed, and supplies at most
36 targets across three disjoint batches. A bounded JSON-schema grammar permits
only objects with a target span ID and replacement. Target IDs are constrained to
the supplied batch; the source offsets/original are resolved from the inventory
and checked against the actual source. Qwen no longer calculates offsets. The
array is bounded to 12 proposals and replacement strings to 120 characters.

The decoder grammar is purely linguistic/structural and contains no evaluator,
watermark configuration or secret information. Batch schema hashes, parse status,
public source spans and seed are saved in candidate-generation metadata.

This correction changes the proposal interface, so **all affected candidate
generation and attacks restart from scratch in a fresh directory**. Feature
definitions, per-sample normalization, weights `(1, 1.25, 1, 1, -1.5)`, hard
filters, `.85` semantic threshold, horizon 8, seeds, budgets and selectors are
unchanged. The revised source/config/protocol are committed before restarting.
The separate development sample yielded 36 validated proposals, 33 passing the
semantic filter, 32 unique candidates and non-overlapping capacity 22. These are
development diagnostics, not benchmark results.

## Source-format validation correction — protocol v3

The restarted candidate stage then exposed an inherited whole-text validator
assumption: original Qwen continuations beginning with `Here is ...` were rejected
as model commentary after otherwise valid localized edits. For example, the seed
bank instructions already began “Here is a concise, safe planning checklist ...”
and the beaver-dam technical explanation already began “Here is a plausible system
model ...”. This prefix came from source generation and was not introduced by SKD.

The attempt at `qwen-v030-r2` was preserved and invalidated, again with an empty
post-attack evaluation file. Protocol `skd-v3` replaces this whole-text heuristic
for SKD only. Both worker and supervisor verify that the output is exactly the
right-to-left application of the selected, independently validated source spans,
with matching source/candidate identities, exact feasible edit count, exhaustion
state and protected anchors. Extra commentary or any change outside those spans
is rejected. The frozen v0.2 validator and baseline behavior remain unchanged.

Regression fixtures cover existing `Here is`, `Here are` and Markdown source
headings, and reject newly added commentary. Candidate generation, language
features, quality filters, weights, seeds and selectors are unchanged from v2.
All candidates/attacks restart in another fresh directory, `qwen-v030-r3`, after
committing this correction. Only the same byte-identical 480 baseline generations
are reused. No attack outcomes entered either correction.
